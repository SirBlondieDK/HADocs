# CA-001 Recommended Cryptographic Architecture

## Decision status

CA-001 recommends exactly one architecture: **HMAC with SHA-256, using the complete 256-bit output and an installation-local secret consisting of exactly 32 octets generated by a cryptographically secure random source**.

This is a proposed architecture decision. It is not implementation, contract activation, a Design Freeze or permission to resume AI-002.

## Inherited requirements

The following requirements are inherited from DF-002, the active contract, R-003 and the AI-002 blocker. CA-001 does not originate them:

- Secret local material participates in opaque-reference derivation.
- Public installation scope alone cannot reproduce the protected derivation.
- Opaque references are deterministic within one preserved installation privacy context.
- Sensitive source identifiers are not practically confirmable from public output alone.
- Secrets and raw sensitive identifiers never enter output, logs or diagnostics.
- References resist collisions and support stable cross-snapshot joins.
- Cross-installation correlation is prohibited.
- Missing or unusable protected material fails closed for the affected capability.
- Independent conforming implementations must be capable of producing identical results from identical normative inputs.
- No network service or external key-management system is required.

## Newly proposed architecture

CA-001 proposes these new normative choices for later review and specification:

1. The keyed primitive is HMAC instantiated with SHA-256.
2. The installation-local secret is exactly 32 octets generated by a cryptographically secure random source.
3. The complete 256-bit HMAC result is retained. It is not truncated.
4. Opaque reference output is derived from the HMAC result rather than AI-001's unkeyed public-scope digest.
5. One cryptographic format version must identify the eventual complete construction, including canonical input framing and domain separation.

No final input bytes, domain labels, prefix, serialization grammar or vector is defined in this batch.

## Why HMAC-SHA-256 satisfies the mandatory requirements

### Security and privacy

HMAC is a standardized keyed construction. A public observer lacking the installation-local secret cannot reproduce the reference derivation merely from public installation scope and guessed identifiers. SHA-256 gives a fixed 256-bit result, retained in full, providing a collision margin appropriate to a persistent identity namespace without a separate truncation decision.

Security remains conditional on the future normative specification correctly defining canonical inputs, purpose separation, secret generation, storage and lifecycle. HMAC does not itself solve those application rules; it provides the selected keyed primitive around which they can be made exact.

### Determinism and interoperability

HMAC-SHA-256 is mature, standardized and available across languages, operating systems and common standard-library or baseline cryptographic APIs. Given the same key and message bytes, independent implementations can reproduce the same full result. This supports straightforward normative synthetic vectors once the message construction is frozen.

### Operational fit

The design requires one installation-local 256-bit secret and no network dependency. It has lower algorithm-availability and dependency risk than less ubiquitous eligible candidates. Its fixed output avoids a configurable-output decision. Its direct keyed construction is operationally simpler than a two-stage derivation-plus-MAC hierarchy.

### Complexity

HMAC-SHA-256 requires fewer architecture parameters than KMAC customization, configurable keyed hashes, extensible-output functions or composed key hierarchies. Canonical framing and domain separation are still mandatory, but they are not coupled to unusual runtime APIs.

## Alternative disposition

### KMAC256 — rejected for this architecture

KMAC256 is technically eligible and offers native customization and configurable output. It is rejected because runtime and standard-library availability is less broad, API interoperability is less uniform, and its configurable output/customization surface introduces additional normative choices without a demonstrated requirement that HMAC-SHA-256 cannot meet.

### Keyed BLAKE2b — rejected for this architecture

Keyed BLAKE2b is technically eligible and efficient. It is rejected because parameter exposure and keyed-mode availability vary more across runtimes, the variant and output-length choices add specification surface, and its dependency/interoperability posture is less uniform than HMAC-SHA-256 for this cross-language contract.

### Keyed BLAKE3 — rejected for this architecture

Keyed BLAKE3 is technically eligible and highly performant. It is rejected because it has narrower default runtime availability, higher dependency risk, a shorter deployment/standardization history for conservative interoperability, and performance parallelism provides little architectural benefit for short metadata identifiers.

### AES-CMAC — rejected for this architecture

AES-CMAC is technically eligible and standardized. It is rejected because its full tag is 128 bits rather than the selected 256-bit identity output, it is a less natural software metadata primitive, and hardware/validated-AES advantages do not offset the lower collision margin and cipher-key operational model for this use case.

### Key-derivation-plus-MAC — rejected for this architecture

A composed derivation-plus-MAC design is technically eligible and offers strong subkey separation. It is rejected because it introduces a second primitive layer, key-hierarchy lifecycle, additional domain/version boundaries and more migration failure modes. The inherited requirements do not demonstrate a need for that complexity; explicit HMAC input domain separation can be specified later without deriving persistent subkeys.

## Normative consequences of adoption

If independently approved and later frozen, adopting this proposal means:

- Every protected opaque reference uses HMAC-SHA-256, not an unkeyed digest.
- The HMAC key is installation-local secret material consisting of exactly 32 octets generated by a cryptographically secure random source.
- Secret bytes are never serialized, logged, exported or supplied by a consumer.
- The HMAC result is exactly 256 bits and is retained in full; truncation is prohibited for this format version.
- Equal canonical input under the same preserved secret yields the same cryptographic result.
- A different secret or different canonical input is a distinct derivation context and is expected to produce a different reference; detected collisions fail deterministically.
- Secret rotation changes every reference derived under that secret and all public identities or relationships that transitively contain those references.
- Missing, invalid, corrupt or unavailable secret material prohibits protected-reference emission and requires fail-closed capability behavior.
- AI-001's unkeyed `ref1_` derivation cannot be treated as byte-compatible with the proposed construction.
- A format-version and migration boundary is required before production adoption.
- Implementations may not substitute another MAC, hash, output length or secret length while claiming conformance.
- Canonical-key and observation-ID algorithms remain unchanged except for downstream values that include the corrected opaque reference; exact byte impact remains to be specified.
- The active contract remains `hadocs-generic-metadata 1.0.0` until separate review and freeze authority changes it.

## Identified but intentionally unspecified work

The normative specification batch must still define:

1. Canonical input fields, ordering, Unicode treatment, framing and byte order.
2. Exact domain-separation values for format, purpose and reference kind.
3. Cryptographic format version, public prefix and output encoding.
4. Secret creation timing, validation and storage abstraction.
5. Backup, restore and migration preservation rules.
6. Rotation authority, prohibited automatic rotation and transitive identity effects.
7. Loss, corruption and recovery behavior.
8. Compatibility and migration from AI-001's proposed unkeyed references.
9. Collision detection and failure boundary.
10. Normative synthetic test vectors and two independent recomputations.
11. Security threat model, residual risks and operational audit requirements.

None of those items is defined by this recommendation. The normative specification batch has not begun.

## Recommendation conclusion

The sole recommended project architecture is **HMAC-SHA-256 with a cryptographically generated 256-bit installation-local secret and the full, untruncated 256-bit HMAC output**.
