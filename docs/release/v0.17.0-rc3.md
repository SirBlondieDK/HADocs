# HADocs v0.17.0-rc3

HADocs `v0.17.0-rc3` is a prerelease focused on making the experimental HASK
candidate flow easier to understand, adding typed Tuya evaluation, and preventing
disabled ZHA diagnostics from becoming analytical signals.

## Highlights

- HASK Preview now distinguishes evaluations from supported candidates and shows
  redacted matcher readiness, bridge state, and safe rejection diagnostics.
- Tuya is the third executable typed matcher and only produces a supported candidate
  when local Home Assistant evidence contains an explicit authoritative problem signal.
- Registry-disabled ZHA LQI entities remain in inventory but no longer pass through
  the remaining raw analytical boundary.
- Bundle `0.2.1` is packaged for supported distribution paths and can be regenerated
  deterministically from validated source data.

## HASK Candidate Readiness

The candidate bridge can use the packaged knowledge bundle without requiring an
explicit bundle path. Preview surfaces separately report matcher records, executable
matchers, candidate evaluations, and supported candidates.

Only `SUPPORTED_CANDIDATE` results are exposed as candidate insights. Blocked or
rejected evaluations remain visible only through bounded, redacted diagnostics.

HASK remains experimental, read-only, and analytically isolated. Candidate output
does not change normal findings, Root Causes, recommendations, severity, device
status, Health Score, or Potential Health Score.

## Typed Tuya matcher

The typed Tuya matcher reports one of these deterministic readiness outcomes:

- `NOT_APPLICABLE`
- `BLOCKED`
- `NO_MATCH`
- `READY`
- `REJECTED_CONFLICT`

A supported candidate requires an explicit authoritative problem signal. Complete,
uniformly healthy Tuya native status produces `NO_MATCH`; missing, incomplete, or
unknown status cannot produce a supported candidate.

The matcher uses only local Home Assistant native integration status. HADocs does
not perform a Tuya or Smart Life login, call a Tuya cloud API, or probe the local
network.

## Disabled ZHA entity scoring

The central disabled-entity eligibility policy now also runs at the remaining raw
analyzer boundary. Registry-disabled ZHA LQI entities cannot become physical problem
signals, while enabled ZHA behavior and existing Z-Wave JS behavior remain unchanged.

Disabled entities are still retained in the installation inventory. User-configurable
entity or domain ignore rules from issue #44 are not included in RC3.

## Privacy and analytical isolation

Public HASK preview and API output remain redacted. Protected installation, database,
scan, observation, relationship, entity, device, and config-entry identifiers are not
exposed.

HASK candidates remain separate from the normal HADocs analysis pipeline and cannot
alter analytical ordering or score calibration.

## Packaging and bundle generation

- Published bundle `0.2.0` remains immutable.
- Packaged bundle `0.2.1` is selected explicitly.
- Python wheel, source distribution, Windows build, and container sources include the
  required `0.2.1` content.
- Source distributions include the generator, its source data, and generation guide.
- The generator validates schemas, identities, duplicate IDs, references,
  relationships, provenance, and typed matcher contracts before writing canonical
  UTF-8 JSON and deterministic checksums.

## Known limitations

- This is prerelease software and should be evaluated before production rollout.
- HASK remains experimental and read-only.
- HASK candidates do not change normal findings, Root Causes, recommendations, or
  Health Score.
- The Tuya matcher uses only local Home Assistant native integration status.
- No Tuya or Smart Life login, cloud API call, or network probe is performed.
- A Tuya config entry with no exposed entities is not yet emitted independently as a
  candidate subject.
- User-configurable ignore rules from issue #44 are not included.

## Upgrade from RC2

Install RC3 over RC2 using the same supported Windows, Docker, or Home Assistant App
path. Existing configuration remains compatible. Review HASK options after upgrade;
they remain disabled unless explicitly enabled. Keep a copy of local configuration and
generated reports before upgrading, and report prerelease findings without attaching
tokens, private URLs, or unredacted installation data.
